# T005 With `--command-target fe_home`, does a MOD SETTINGS row press reach `FeHome_Handle_Command` while the settings screen is open?

- Requested by: native-agent (settings bridge), 2026-10-17
- Status: draft
- Session: (filled by the lead when batched). Separate launch from T004 (different UI data, same hook target).

## Question
If the v8 rows raise their commands on `fe_home.raise_command` instead of the settings screen's own pin (`tools/build_home_tile_mod.py v8 --command-target fe_home`, `research/mod-settings.md` §6), does `FeHome_Handle_Command` receive them while `swofty_settings` is open and fe_home is closed?

## Hypothesis
- `research/ui.md` §7, "Cheap test": route `fe_home.mod_menu` closes fe_home and opens `swofty_settings`, the same sub-page transition Career uses. If command routing goes by live screen instance, a command aimed at the closed fe_home is dropped.
- If fe_home's view model stays alive across the sub-page (Career returns to it without a rebuild), the command reaches `FeHome_Handle_Command` (0x141bb3c20, L3) with `[rdx]` = a `NeStr` whose hash is the djb2 of the full name. fe_home ignores unknown hashes (`re/decomp/141bb3c20.c` falls through on an unmatched hash and returns rax), so the press is harmless either way.
- The settings bridge (`native/src/core/settings.cpp`, `research/mod-settings.md` §7) matches exactly that hash in its wrap on `FeHome_Handle_Command`, so a pass makes the fe_home target the working route until T004's dispatcher hook exists.

## Promotes
- Pass: `FeHome_Handle_Command` gains `trace:T005/<run>:<line>` for a data-defined command name. The `fe_home` command target becomes the supported v8 route. KB note on `FEHomeViewModel`: alive and receiving commands while a sub-page is open (same `a0` as at home).
- Fail: note that fe_home's pin is dead while the sub-page is open. The bridge then depends on T004's result.

## User steps
1. Install as above and launch as usual. Reach the home menu.
2. At home, move focus down one tile and back up.
3. Press F9 (or R3) to open MOD SETTINGS. Write down the clock time.
4. Press Select twice on SHOW LAUNCHER PANEL. If a slider or choice row is shown, press Right once and Left once on it. Press Select once on another mod's ENABLED row. Write down the clock time.
5. Back to home, then quit the game.
6. Send `swofty/trace.log`, `swofty/loader.log` and the two times.

## Expected log lines
Regexes against `swofty/trace.log`:
- `^H .* status=active hooks=1 installed=1 rejected=0` → hook installed.
- `^E .* hook=t005\.fehome_cmd .* a0=(0x[0-9a-f]+) .* cmd=0x70d928ee:"focus_changed"` → baseline at home; note `a0`.
- Between the two noted times: `^E .* hook=t005\.fehome_cmd .* cmd=0x2646b95e:"swofty_set:swofty\.core:show_launcher_panel:0"` and `cmd=0x2646b95f:"…:1"` → the press reaches `FeHome_Handle_Command` with the djb2 hash the bridge matches. An ENABLED press shows `cmd=0x[0-9a-f]+:"swofty_enable:<mod>:[01]"`.

Pass: the `swofty_set` lines appear between the noted times, each hash equals the djb2 of its chars, and the game keeps running. Fail: `focus_changed` lines at home but no `swofty_set` line while the settings screen is open (dropped). Inconclusive: the plugin is not active.
