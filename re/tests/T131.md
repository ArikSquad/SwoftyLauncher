# T131 How large are the SAVE_PROPERTY_BAG_TEMP pool and its peak use at a profile load and a profile save, without a swofty_registry entry and with 64 KB and 256 KB entries?

- Requested by: w4r, 2026-10-28

- Session: (filled by the lead when batched)

## Question
How large are the SAVE_PROPERTY_BAG_TEMP pool and its peak use at a profile load and a profile save, without a swofty_registry entry and with 64 KB and 256 KB entries?

## Hypothesis
`subsystems/game.md#save-heaps`. A profile load decodes the whole profile into a pool made from the largest free block of SAVE_TEMP_ALLOC_HUGE (200M) or SAVE_TEMP_ALLOC (75M), and a profile save into one from SAVE_TEMP_ALLOC; `Game_CompressedSave_FreeTempPool_Thunk` logs its size and peak when it frees it. Expected: pool size in the tens of MB, load peak a few MB on swofty's profile, and each entry adds about 1.4x its payload to the load peak (base64 plus string headers) and nothing to SAVE_DATA. Nothing logs an `Ne heap error`.

## Promotes
- `Game_CompressedSave_OnReadResult` (pool notes), `Game_CompressedSave_FreeTempPool_Thunk`, `Game_CompressedSave_GetTempHeaps`, `g_Game_SaveTempAllocHeap`, `g_Game_SaveTempAllocHugeHeap`, `Ne_BagCodec_ReadBag`, `Ne_Bag_ReadValue`, `Ne_Bag_Clear`: L2 -> L3 (L1 -> L2 for `Ne_Init_TempPool_Thunk`).
- A load peak that does not grow with the entry, or an `Ne heap error` naming SAVE_DATA at a load with the entry, demotes the pool claim.

## Build

## Trace config
None. `SWOFTY_GAME_LOG_CHANNELS=default,CompressedSaveDataSerialiser,SaveGame` so the pool lines land in `loader.log`. The entry sizes come from the snapshots' own `[saves]`/snapshot lines.

## User steps
Scratch protocol of T010 (live saves backed up first, restored byte-identical; Steam Cloud off; own the game lock).
1. Run A, no snapshot registries enabled (no entry): to the main menu, force a profile save (toggle one Game Options setting and back), quit.
2. Run B, a test registry that freezes about 64 KB per career, one Driver Career loaded to Team HQ and saved: quit from the main menu, start again to the main menu, force a profile save, quit.
3. Run C, the same with about 256 KB per career.
4. Restore the live saves.

## Expected log lines
- `PropertyBagTempPool size=(\d+) sizeUsed=(\d+) peak=(\d+)` at each load and each save → the pool size and peak (record all three per run)
- `\[saves\] profile load \d+: kept swofty_registry \((\d+) bytes\)` in runs B and C → the entry's bag size
- none: `Ne heap error`, `could not keep`
Pass rule: every load and save logs a pool line, the load peak in B and C exceeds A's by at most about 2x the kept entry bytes, and no heap error. Fail rule: a heap error, a crash at load, or no pool line.

## Procedure with the pad knob (added by w31)
`SWOFTY_TEST_SNAPSHOT_PAD=<bytes>` makes the next profile save write a swofty_registry entry holding a filler item of that size, with no season start and no snapshot needed. The core reads it once at the snapshots setup and only in a live `swofty test` run (the agent is armed and the run token is still in run.json); anywhere else it logs `SWOFTY_TEST_SNAPSHOT_PAD ignored (the test agent is not armed)` and does nothing. Values outside 1..4128768 are ignored. The pad is one write only: the entry stays in the save afterwards as an unknown item, and the next load keeps it.
1. Core and loader from a build with the knob (`native/build.sh`; record the `swofty_core.dll` md5). Save sandbox on (T010 protocol), the profile saves backed up first.
2. Run A: no variables. To the main menu, force a profile save (toggle one Game Options setting and back), quit. Record the `PropertyBagTempPool` lines.
3. Run B: `SWOFTY_REGISTRY_SAVE=on SWOFTY_TEST_SNAPSHOT_PAD=65536 SWOFTY_GAME_LOG_CHANNELS=default,CompressedSaveDataSerialiser,SaveGame`, started with `swofty test` (benchmark or boot environment, sandboxed). Load the career to Team HQ, force a profile save, quit. Start again the same way to the main menu without the pad variable (the entry loads from the save), force a profile save, quit.
4. Run C: the same with `SWOFTY_TEST_SNAPSHOT_PAD=262144`, from the fixture's profile (a fresh sandbox copy so run B's entry is gone).
5. Restore the live saves.
Extra log lines: `\[registry\] test: SWOFTY_TEST_SNAPSHOT_PAD set; the next profile save writes a (\d+)-byte filler` at startup, `\[registry\] swofty_registry: this profile save writes a (\d+)-byte entry` at the save, `\[saves\] profile load \d+: kept swofty_registry \((\d+) bytes\)` at the next load. Without `SWOFTY_REGISTRY_SAVE=on` the save is dry and logs the entry it would have written, so the pad is never written to a real profile by accident.
Host test: `native/test/run_snapshots_test.sh` (the `test pad:` lines).
