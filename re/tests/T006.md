## Question
Does every screen raise_command and every allowVMBinding screen activation reach Vm_Dispatch_BindingMessage (0x1442c00e0) as VmMessage type 0x4c/0x4d keyed by djb2(screen name), including commands from swofty_settings, which has no view model?
One question only. If it splits into two, file two tests.

## Hypothesis
- `Vm_Behaviour_HandlePin` (0x1442860c0) turns every `raise_command` on a screen that carries the ViewModelBehaviour (`NBVM`) into a VmMessage of type 0x4c `{+0x14 node id = djb2(screen), +0x20 name NeStr*, +0x28 data}` and queues it, whether or not a VM is bound.
- `Vm_Behaviour_OnNodeMessage` (0x144284fd0) queues type 0x4d with ev 0 on activation (and ev 3 when the node allows VM binding); deactivation queues the closing events.
- `Vm_Dispatch_BindingMessage` (0x1442c00e0) consumes both. For fe_home the node id is 0xa1fedfb8 = djb2("fe_home") and `select_pressed` arrives as name hash 0x02b0357a. For `swofty_settings` (v11a, no `allowVMBinding`) the commands still arrive with node 0x90c2d901 = djb2("swofty_settings"), and then are dropped, because that node never registered a binding entry (research/ui-native.md section 2).

## Promotes
- `Vm_Dispatch_BindingMessage` L2 -> L3, and the raw signature becomes KB signature `vm.dispatch_binding_message`.
- `Vm_Behaviour_HandlePin`, `Vm_Behaviour_OnNodeMessage`: stay L2, but the message shape (`VmMessage.type`, `.node_id`, `.arg`) gets `trace:` evidence.
- Fail (no `node=0x90c2d901` lines while MOD SETTINGS rows are pressed): commands of a screen without a binding entry are dropped before the queue; `on_command` for VM-less screens then needs the pin handler (0x1442860c0) instead. Nothing is demoted.
