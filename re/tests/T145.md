## Procedure with the probe DLL (added by w31)
The hook points `ai.controller.update` (per AI car, every frame if it fires) and `car.controllers.rebuilt` are the 1.6 views of the two sites; the probe subscribes to both with the standard `after` phase and counts them. It does not trace the raw addresses (0x143895940, 0x14389a120); do that afterwards with a trace config if the counts say the point fires.
1. Build (not shipped, not part of `native/build.sh`): `native/test/build_t145_probe.sh` writes `native/build/t145/t145_probe.dll`. Core and loader from a 1.6 build with the hooks table (`native/build.sh`).
2. Install: copy `t145_probe.dll` into `<game>/swofty/addons/` (the loose-addon folder, next to nothing else it needs). Remove it after the run.
3. Run: `swofty test` with a benchmark environment (`{ "kind": "benchmark", "track": "bahrain", "laps": 2, "cars": 10 }`, AI cars on track, no input) and `SWOFTY_GAME_LOG_CHANNELS=default`; let the race run 60 s, then quit. The save sandbox applies as for any test.
4. Read `swofty/loader.log`. Each second with any hit logs one line per vehicle and a summary:
- `\[t145\] probe installed: after ai.controller.update ok, after car.controllers.rebuilt ok, on_frame ok` → both subscriptions took (anything other than ok names the missing table or point)
- `\[t145\] second \d+ vehicle (\d+): ai.controller.update ([\d.]+)/s \((\d+)\), car.controllers.rebuilt (\d+) \(resettle (\d+)\), threads ([\d,-]+)` → rate per vehicle, rebuilds, and the game threads the point fired on
- `\[t145\] second \d+: no ai.controller.update and no car.controllers.rebuilt yet` every 10 s → neither point fires
Pass rule: every AI vehicle shows a rate near the frame rate (60/s expected) from the race start and one `car.controllers.rebuilt` per car near it; one thread id. Fail rule: no vehicle line after the lights go out, or a rate of zero for some AI cars (then the point fires only for some controllers or not per frame). The human car shows no `ai.controller.update` line.
