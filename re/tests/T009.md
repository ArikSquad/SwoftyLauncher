# T009 Does a profile save in a session without a career content addon keep that addon's mode save container (driver_career_progressive) so its careers list again once the addon is back?

- Requested by: keepsaves, 2026-10-27
- Status: run, failed (keeper removed)
- Session: (filled by the lead when batched)

## Question
With the save keeper in core, does a session without the Progressive Career addon load and rewrite the profile save without dropping the `driver_career_progressive` container, so the Progressive careers list and load again in the next session with the addon?

## Hypothesis
`subsystems/game.md#save-containers`: the Progressive mode row registers its own top-level container `driver_career_progressive` under the save root, and its slot manager holds every Progressive career. Without the addon, `Game_SaveData_DeserialiseContainer` drops that child bag at the profile load because the root's `SaveDataContainer.retain_unknown` is false, and the next profile save writes the root without it (the 2026-10-26 22:07 and 23:33 losses: 929,672 -> 871,272 bytes). The keeper sets `retain_unknown` on the root (`vt_Game_SaveDataRootContainer`) before each root load; the bag then sits in the retained map (`SaveDataContainer.retained_count`) and `Game_SaveData_SerialiseContainer` / the inline twin write it back unchanged.

## Promotes
- `Game_SaveData_DeserialiseContainer`, `Game_SaveData_SerialiseContainer`, `vt_Game_SaveDataRootContainer` (sig `game.save_data_root_container`), `SaveDataContainer.retain_unknown`, `SaveDataContainer.retain_unknown_key`, `SaveDataContainer.retained_count`: L2 -> L3.
- A fail at step 9 (careers missing after the keeper ran) demotes the write-back claim of `Game_SaveData_SerialiseContainer` and the keeper must not ship.

## User steps
Never use swofty's live saves. Every run uses a scratch copy of an old backup, and the live files are restored byte-identical at the end. Own the game lock for the whole test.
1. Quit F1 25. In Steam, F1 25 > Properties > General: turn off "Keep game saves in the Steam Cloud".
2. Back up the live saves: `cp -a ~/.local/share/Steam/userdata/843502855/3059520/remote /mnt/work/f1-save-backups/$(date +%Y%m%d-%H%M%S)-T009-live` and write `sha256sum` of every `savegame@*` file into `MANIFEST.sha256` there.
3. Scratch save: copy `savegame@profile#NXDSMWW.BWW` and `savegame@profile#QKRHMYXE` from `/mnt/work/f1-save-backups/20261026-224729-mp-smoke/` (the backup that still holds the Progressive slots, 929,672 bytes) over the live ones in `remote/`. Record size and sha256 (S0).
4. Run 1, profile A (with the addon): start to the home screen. Career > Driver Career, Addons row, Progressive tile: write down every career slot listed (name, team, season). Back out without loading a career and quit from the main menu. Record size and sha256 (S1) and keep `loader.log` (run1).
5. Run 2, profile B (without the addon): start to the home screen. Career > Driver Career > 2026 tile: the stock careers list as usual; continue one to Team HQ and back out to the main menu without saving.
6. Still in run 2, force a profile save without touching a career: Settings > Game Options, change one harmless option, back out (the game saves the profile), change it back, back out again. Quit from the main menu. Record size, sha256 and mtime (S2) and keep `loader.log` (run2).
7. Check: S2's mtime is after run 2 started (the profile was rewritten) and S2's size is within a few KB of S1 (not about 58 KB smaller).
8. Run 3, profile A again: Career > Driver Career, Addons row, Progressive tile.
9. Check: the same slots as in step 4. Continue the first one to Team HQ, then quit from the main menu without saving. Keep `loader.log` (run3).
10. Control, on a fresh scratch copy only (repeat step 3 first): set `SWOFTY_KEEP_UNKNOWN_SAVES=0` for the session and repeat steps 5 and 6, then step 8 without the variable. Expected: the file shrinks by about 58 KB in step 6 and the Progressive tile lists no careers, which shows the keeper is what keeps them.
11. Restore: delete the scratch `savegame@profile*` files, copy the live ones back from step 2's backup, and check them against `MANIFEST.sha256`. Turn Steam Cloud back on and check that Steam reports no conflict.

## Expected log lines
- run 1, 2, 3: `\[saves\] unknown save container keeper armed` → the wrap installed
- run 2: `\[saves\] profile load \d+ \(result 0\): kept ([1-9]\d*) save container\(s\) that no loaded game mode claims` → the root kept `driver_career_progressive` (its count is run 1's count plus 1; run 1 may report other unknown containers, such as a `driver_career_1990` left by the F1 1990 tests)
- run 1 and 3: `\[saves\] profile load \d+ \(result 0\): (every save container is claimed|kept \d+ save container)` → the load succeeded
- none: `could not turn on keeping unknown save containers`, `keeper did not install`
Pass rule: the run 2 line with a count at least 1, step 7 holds, and step 9 lists and loads the same Progressive careers. Fail rule: the run 2 count is 0, S2 is about 58 KB smaller than S1, a Progressive career is missing or fails to load in step 9, a stock career fails to load in step 5, or any profile load reports a non-zero result.

## Result
- Run id: 2026-10-27 coordinator session 20261026-142820, core from origin/main plus `fix/keep-addon-career-saves` at 10eadbb5, scratch save from `20261026-224729-mp-smoke`.
- Run 1 (with Progressive): `[saves] unknown save container keeper armed` and `profile load 1 (result 0): every save container is claimed`. Pass.
- Run 2 (without Progressive): crash at the profile load, before any save: `Ne heap error 0xc (fatal) ... Requested size:16368, Free Memory:5200, Largest Free Block:4048, HeapSize:3145728 ... heap 'SAVE_DATA'`, stack keeper wrap -> `Game_SaveData_DeserialiseContainer`+0xd57 (the retain copy 0x143931350) -> 0x1439328d0/0x1439315fd recursion -> heap. The save file was not written. Report `crash-20261027-012856.txt` in that session's game-logs.
- Verdict: fail. The retain path copies the unknown bag into the 3 MB `SAVE_DATA` heap, which the decoded profile already fills. Static follow-up: the profile save uses the inline serialiser `Game_SaveData_SerialiseContainer_2`, which never writes retained bags, so the approach could not keep the careers even with a bigger heap. The keeper was removed from core; the KB rows stay at L2 (their static claims hold; `game.md#save-containers` records the failure and the splice design).
