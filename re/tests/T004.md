# T004 Which native function receives a `raise_command` fired by a node of the `swofty_settings` screen?

- Requested by: native-agent (settings bridge), 2026-10-17
- Status: draft
- Session: (filled by the lead when batched). Needs its own launch: T005 uses different UI data and the same trace hook target.

## Question
When a row of the MOD SETTINGS screen (`swofty_settings`, the second screen in `fe_home.ui`, no native view model, `research/ui.md` §4c) raises `swofty_set:<mod>:<option>:<index>` on its own `raise_command` pin (v8, default command target, `research/mod-settings.md` §6), which native function receives the command, so that the settings bridge can hook it?

## Hypothesis
- Commands are matched by djb2 in native code (`research/ui.md` §5). A screen's `raise_command {name}` is delivered to its view model's virtual `onCommandRaised(const neon::NeUIString &, const neon::NeUIPrimitiveType &)` (`re/db/strings_anchors.tsv`, `s_FEHomeViewModel_onCommandRaised` and the eight `*_OnCommandRaised` rows). At the function start: rcx = view model, rdx = the name (`NeStr *` at `[rdx]`, `NeStr.hash` at +0), r8 = the data value.
- `FeHome_Handle_Command` (0x141bb3c20, L3, sig `fe_home.on_command_raised`, xref 0x145738ab0 = its vtable slot) is fe_home's override. Its caller is the generic UI layer that turns a node's `raise_command` pin into that virtual call (`research/ui.md` §7, "Where to hook").
- `swofty_settings` has no view model (fe_home's behaviour list without `F1FS`), so its commands probably stop in that generic layer and reach no `*_OnCommandRaised`. Two receivers are traced anyway:
  - `FeHome_Handle_Command`, in case routing goes by flow or scene rather than by screen.
  - `Game_FrontendTransitionViewModel_OnCommandRaised` (0x141bb8a20, L1). It is the only flow-level view model among the KB's `*_OnCommandRaised` rows, and is the likeliest fallback receiver for a screen without its own. Its prologue (`mov rbx, r8; mov r14, rdx`) has the same three-argument shape.
- Expected result: neither hook sees a `swofty_set:` name while MOD SETTINGS is open. Then the `ret`/`bt` frames of fe_home's own commands (`focus_changed` 0x70d928ee, `select_pressed` 0x02b0357a, `back_pressed` 0x493fe92b) name the dispatcher chain, and a follow-up test hooks that dispatcher, filtered on the `swofty_set` hashes.

## Promotes
- Any outcome with E lines: the `ret` frame and `bt` frames 1–2 of `t004.fehome_cmd` get KB rows (L2, `trace:T004/<run>:<line>`) as the command dispatcher chain. The first 16 bytes of `NeUIPrimitiveType` (`data`) go into a struct note.
- `t004.transition_cmd` logs any command: `Game_FrontendTransitionViewModel_OnCommandRaised` L1 → L2 (runtime function start and argument shape), and the raw signature below becomes KB signature `fe_flow.transition_on_command_raised`.
- A `swofty_set:` name on either hook: that function is the bridge's hook target. Its row goes to L3 with this trace, and the bridge wraps it the way it wraps `FeHome_Handle_Command`.
- Demotes: none. `FeHome_Handle_Command` stays L3. If `t004.transition_cmd` is rejected with `not_function_start`, the L1 row's address is wrong (the string may belong to an inlined callee); note it on the row.

## User steps
1. Install as above and launch as usual (bypass.exe, then F1_25.exe). Reach the home menu.
2. At home, move focus down one tile and back up. Wait two seconds.
3. Press F9 (keyboard) or R3 (controller) to open MOD SETTINGS. Write down the clock time.
4. On SwoftyMod's SHOW LAUNCHER PANEL row, press Select twice (OFF, then ON). On another mod's ENABLED row, press Select once. Write down the clock time.
5. Press Back to return home, then quit the game from the home menu.
6. Send `swofty/trace.log`, `swofty/loader.log` and the two times.

## Expected log lines
Regexes against `swofty/trace.log`:
- `^H .* result=match` → build check passed.
- `^H .* status=active hooks=2 installed=2 rejected=0` → both hooks installed. `t004.transition_cmd` alone rejected (`not_function_start`) still lets the test answer through `t004.fehome_cmd`.
- `^E .* hook=t004\.fehome_cmd .* cmd=0x70d928ee:"focus_changed" .* ret=0x14[0-9a-f]+ bt=0x14` → fe_home's commands arrive; `ret` and `bt` name the dispatcher chain. These frames are the main result.
- Between the two noted times:
  - `^E .* hook=t004\.(fehome|transition)_cmd .* cmd=0x2646b95[ef]:"swofty_set:swofty\.core:show_launcher_panel:[01]"` → that function receives the screen's commands (outcome A). `0x2646b95e`/`0x2646b95f` are the djb2 of the `:0`/`:1` names.
  - no line with `swofty_set` → the commands stop before any traced view model (outcome B, expected).

Pass: outcome A, or outcome B with at least one `t004.fehome_cmd` E line whose `ret` and first `bt` frames lie in F1_25.exe. Fail: no `t004.fehome_cmd` E line at all, or a crash that does not reproduce without the plugin. Inconclusive: the plugin is not active (check the `H`/`R` lines).

On outcome B, the follow-up hooks the function containing `bt` frame 1 (the caller of the virtual call) at its function start, with the name's location found from its decompile, filtered by `when: ["u32:[[rdx]] == 0x2646b95e"]` or the equivalent register.
