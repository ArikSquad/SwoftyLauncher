# game: game:: code named from pretty-function strings

Owner: see `subsystems.tsv`. Source: the bulk naming pass of 2026-10-17.

## Map
- Every row here is L1. Its name comes from a `__PRETTY_FUNCTION__` or log string that the function references (`str:` anchor plus `xref:` sites); the full C++ name is in `notes` as `cxx=`.
- A function was named only when it references exactly one such name and no other function references that name. Names shared by several functions are kept as anchors only, since they usually mean an inlined callee.
- The string can still belong to a callee inlined into the named function. Read the decompile before raising a row to L2.
- Rows move to a feature lane (`session`, `fe_home`, ...) when someone takes them on; rename to `<Prefix>_<Verb>_<Noun>` at that point.
- neon:: names from the same pass are in `core` (prefix `Ne`, class `Ne` prefix dropped). The exe has no `ego::` strings.
- Hand-raised rows (not from the bulk pass): `g_Game_Root` (0x14601db08), the root object whose +0xa0 context holds the UI module at +0x28 (see core.md, fullscreen video), and `g_Game_FlowLinkStay` (0x146cb2280), the link a flow state's onUpdate writes to stay put; `g_Career_FlowLinkContinue` follows it at 0x146cb2284.

## Save containers
<a id="save-containers"></a>
Raised by keepsaves (2026-10-27, static, Steam d873a1c8) for the lost Progressive careers.
- The profile save (`savegame@profile#NXDSMWW.BWW`) is one tree of save-data nodes (`structs/SaveDataContainer.h`, base ctor `Ne_Construct_SaveDataContainer` 0x14364d570). Its root `save_game` is `SaveDataSystem+0x20` (`Game_SaveDataSystem_Construct` 0x143654650, `vt_Game_SaveDataRootContainer`).
- Every `game_modes` row with `register_save_container` true puts its mode container, named by `save_data.name`, directly under the root (`Game_GameModes_BuildMode` 0x1407cae80, attach at 0x1407cf910). The mode's `SaveSlotGameModeComponent` (`Game_SaveSlotManager_Construct` 0x1429cd140, built in `Game_ModeChampionship_Build` at 0x1407d5b62) holds every career slot of that mode with its raw data blob (`Game_SaveSlotManager_Deserialise` 0x1429d6810, `Game_SaveSlotManager_LoadSlot` 0x1429d42f0). Slots are never validated against the database at load (`Game_SaveSlotManager_ReadSlotInfo` 0x1429d4a30 only copies fields).
- Load: `Game_SaveData_DeserialiseContainer` (0x14364f3a0, entered for the root from .data1 at 0x150b20d82) matches each child bag of `containers` to a registered child by FNV-1a64 of the name. A child bag nobody registered is dropped, unless the node's `retain_unknown` bool (+0x100/+0x108) is true: then the bag is copied into the node's retained map (+0x190, count +0x1c8). The root is built with `retain_unknown` false.
- Save: the bag-path `Game_SaveData_SerialiseContainer` (0x14364e000) writes the registered children and, with `retain_unknown` true, every retained bag back under its own name. The profile save does not take that path: the .data1 save at 0x150b16391 calls `Game_SaveData_SerialiseTimed` with no bag and a stream, so the root goes through the inline twin `Game_SaveData_SerialiseContainer_2` (0x143651030), which writes only the registered children and never reads `retain_unknown` or the retained map.
- So a career content whose mode row has its own `save_data.name` (Progressive: `driver_career_progressive`, statId 82; F1 1990: `driver_career_1990`) loses every career the first time the profile is saved in a session that lacks the addon: the mode container is not registered, the root drops its bag at load, and the next profile save writes the root without it.
- Names resolve: the profile is written with the inline encoding (key strings in the stream), and the stream reader 0x143934620 (called by `Game_CompressedSave_OnReadResult` 0x14364bb50) adds every key with the bag add-by-name 0x143932a40, which registers the name in the string table 0x146129740 that the retain path looks the bag hash up in (0x14392a8b0).
- Turning `retain_unknown` on for the root does not fix the loss and crashes the game (T009 run 2, 2026-10-27): the retain path deep-copies the unknown bag (0x143931350) into the 3 MB `SAVE_DATA` heap while the decoded profile bag still lives there, and the copy of `driver_career_progressive` failed with Ne heap error 0xc (requested 16,368, free 5,200). Even with room, the inline profile save would not write the retained bag. A keeper has to hold the bytes outside the game heaps and splice them into the inline stream: the stream codec is vtable 0x14568e060 (+0x8 bag writer 0x1439340c0, +0x10 bag reader 0x143934620, +0x18 header value 1), and the root's `containers` block in 0x143651030 is a child count followed by name, type id and body per child.

### Keeping unclaimed containers by bytes
<a id="save-splice"></a>
Raised by splicesaves (2026-10-27, static). The bytes of an unclaimed root child are kept outside the game heaps and written back into the inline profile save.
- Load: `site_Game_SaveData_UnclaimedChild` (0x14364fef0) is the no-match join of the child loop in `Game_SaveData_DeserialiseContainer`; rdi = the container, `*[rsp+0x88]` = the property of the current child bag. For the root (`vt_Game_SaveDataRootContainer`) the property's key hash (`NePropertyTypeVtbl.key_offset`) gives the name through `Ne_StringTable_Lookup`, and `NePropertyVtbl.value` gives the bag. `Game_SaveData_WriteBag` writes it through a `NeBagCodec` twice, as `0x1429ce380` does for a career slot: into a `NeCountingStream` for the size, then into a `NeMemWriteStream` over a buffer the core owns. Only bag-typed children are kept (type id against `k_Ne_PropertyType_Bag`).
- Format: the root's `containers` block in `Game_SaveData_SerialiseContainer_2` is the key, the bag type id (u32), the codec header (8 bytes, 1), the child count (8 bytes), then per child its name (stream vt+0x50 length byte, vt+0x48 chars), the bag type id `[rsp+0x58]` (u32) and its body. The reader `0x143934620` reads every child body as a bag, and `Game_SaveData_WriteBag` is its inverse, so name + type id + the captured `WriteBag` bytes is an entry the next load reads back as the same bag.
- Save: `site_Game_SaveData_ContainersCount` (0x143651bbf) adds the kept count to `[rsp+0x90]` before the count is written; `site_Game_SaveData_ContainersChildren` (0x143651be4) writes the kept entries to `[rsp+0x50]` right after it. A failed write stores the code in `[r12]` and continues at `site_Game_SaveData_ContainersDone` (0x143651cbc), the game's own path for a failed write in that block.
