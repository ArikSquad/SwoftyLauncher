# core: neon engine basics

Owner: see `subsystems.tsv`. Write-up: research/exe.md §1.

## Map
- `NeStr` (`structs/NeStr.h`): +0 djb2 hash, +4 refcount (u16), +6 24-bit length/flags, chars from +9. A null pointer means "" (hash 0x1505). `Ne_Make_StrFromCStr(NeStr** out, const char*, flags, len)` creates or reuses one (T000: works from a mod thread at the home build).
- Allocators (`structs/NeAllocator.h`): vt+0x18 `alloc(self, size, align)`, vt+0x38 `free(self, p)`. `g_Ne_DefaultAllocator` (0x146ca54a8) is used for frees in the adders.
- `Ne_Format_String` (0x1441630f0) is the sprintf used for `button_%d`.
- Engine setting getters (`xanpavle.re-optimization`): `Ne_Get_SettingBool` (0x143a43b90) and `Ne_Get_SettingU32` (0x143a43240) take `(node, name, out, def)`, lock node+0x10, look the name up in the map at node+8 and convert the text value into `*out`; on a missing name or a failed conversion they store `def` and return 2 or 0x53. Integers go through 0x143919770 (strtoul, 0x hex, K/M/G), floats through the sibling getter 0x143a43ea0. Callers read names such as `Renderer.Gfx.enableVRS` (0x1443cc6b7) and `Renderer.Gfx.groundCoverMaxInstances` (0x14014d448).
- Hardware settings XML: `Ne_Init_HardwareSettings` (0x14401c700) parses `system/hardware_settings_config.xml` (or `_vr`) into the doc 0x146044700 through `Ne_Load_XmlFromMount` (0x14401da80, parse call `site_Ne_HwXmlParseCall`), then the player's copy through its own `_wfopen` + `fread` + parse (`site_Ne_HwConfigParseCall`). Both hand `Ne_Parse_XmlDoc_Thunk` (0x1440142c0, a .data1 thunk) a reader whose +8 is a MemStream `{vtable, data, size, pos}`; the caller frees its own buffer pointer after the parse. `Ne_Save_HardwareSettings` (0x14401e350) writes the doc with `Ne_Save_XmlDoc` (0x14401ebd0), which serialises it and calls `fwrite(text, 1, len, f)` at `site_Ne_HwXmlWriteCall`. The first load is reached from the startup function 0x1401780c0 only after its `CreateMutexW("Codemasters F1 25")` call (0x1401790ee -> 0x1443e0ad0 -> 0x1443c0560 -> 0x1443c4fa0 -> 0x1443c5e24), so a plugin loaded at the early stage hooks it first.
- Build facts: clang unity build `F1_2025_VS2022_win64_steam_master_dx12_clang_unity.exe`; no RTTI; `__PRETTY_FUNCTION__` strings in asserts recover class and method names (search strings_ascii.txt for `game::`).
- Fullscreen video (`Ne_Play_FullscreenVideo`, 0x14416de50, `neon::NeUIGenericFeatureSystem::playFullscreenVideo`): `(feature_system, NeStr **path, {void (*fn)(void *ctx); void *ctx} *on_end, frame_callbacks, layer)`. The feature system is `(module+0x10)->vt[0xf0](module+0x10)`, module `*(*(g_Game_Root+0xa0)+0x28)`. Its player (`NeUIFullScreenVideo`, feature system +0x108) keeps `on_end` at +0xd0/+0xd8 and calls `fn(ctx)` from its update (0x14421dbf0) when the video ends or is stopped; 0x14416e6a0 stops it. The open (0x14421c750) adds `videos/` to a path without it, and the video service's onOpen (0x143f82d40) hands Bink the relative path: `.bik` plays as Bink 1 (BT.601 limited-range matrix), `.bk2` as Bink 2 (full range); `bink2w64.dll` checks the `BIKf`..`BIKk` headers too. Skipping is the `AllowVideoSkip` bus message (bool at +0x10): `PersistentFlowViewModel` (0x14165b240) sets `skip_allowed` and a start time, and its input handler (0x14165a660, action 0x3117db12) stops the video after 2 s. `Ne_Post_BusMessage` finds subscribers by the name `msg->vtbl[1]()` returns (FNV-1a + strcmp).

## Bindings across builds
- Spec: `re/PROTOCOL.md` §10.
- `re/tools/bindgen.py` writes `bindings.json` for the KB build (Steam) and `bindings.<build>.json` for every other overlay in `re/db/builds/` (`bindings.ea.json`).
- Every set holds the same gated bindings with the same patterns, resolves, anchors and statuses; an overlay changes only sections, overridden patterns, hints and unresolvable entries.
- Core picks the set whose `build.pe_timestamp` matches the running exe and resolves each binding the same way on every build: verified `match` hint, then section scan, then string anchor.
- `build.packed: true` marks a build whose code section is encrypted on disk; core resolves and hooks its code bindings once that code reads decrypted.
- The EA App build (sha256 `cc506879c1c834aa…`, pe_timestamp 1789128892) is packed: its engine code is in `.rdata` (Steam `.xtls`), its RWX `.xcode` sits where Steam has `.data1`, and the code is bulk-decrypted by the window stage.
- `re/db/ea-targets.json` and `re/db/signatures.ea.json` were retired on 2026-10-22; their fixed EA targets were dropped and the scan replaces them.
- On the EA dump `F1_25.1789128892.110548.mem`, `re/tools/bindverify.py` resolves all 299 EA bindings by hint and all 299 by scan, and the 11 exported string anchors locate the same targets on both builds.
- `site_Ne_HwBool_NightShadowCharCast` needs an EA override: the Steam pattern ends on .data1 protector filler and matches once on EA at a call to `__security_check_cookie`.

## Save device and the test sandbox
<a id="save-sandbox"></a>
Raised by ts3 (2026-10-28, static, Steam d873a1c8) for the `swofty test` save sandbox. Decomps: re/decomp/144137890.c (init), 14413af70.c (Start), 14413b6f0.c, 144144920.c, 144145650.c, 1441490a0.c, 144152070.c, 14413a6d0.c, 144141c00.c, 1447c5bc0.c, 144143580.c, 1407f7320.c.
- Build (`Ne_SaveSystem_InitDevice` 0x144137890, called once from `Game_Read_GameConfig` at 0x1407fa7c0): the device is 0x3f0 bytes, `vt_Ne_SaveSystem2Win` (0x145a5c640, 16 slots), stored at save system+0x490. Fields: +0x08 allocator, +0x18 save system+0x50 (whose +0x70 is the wide title save dir, `g_Ne_TitleSaveDir` contents), +0x20 save system+0x2d0 (cipher key source), +0x30 Steam helper, +0x268 uploader (`vt_Ne_CloudUploader`), +0x330 64 KB work buffer, +0x338/+0x340 cipher objects (made by Start), +0x3e8 `m_storeInCloud` = save system+0x498.
- Helper (0x110 bytes, built only when `g_Ne_SaveSteamEnabled` 0x14604e0ec is set): +0x108 = `*SteamInternal_ContextInit(k_Ne_SteamRemoteStorageContext)` (STEAMREMOTESTORAGE_INTERFACE_VERSION016), then `ISteamUser022` vt+0x30 `GetUserDataFolder(char *helper, 0x104)` fills +0x00 as an ANSI string. Order at 0x144137c4b..0x144137c9f: helper+0x108, helper+0x00, device+0x30 = helper, save system+0x490 = device, then `call [vt+0x08]` = `Ne_SaveSystem2Win_Start`. Nothing touches remote storage before Start, and Start itself never touches the helper. 0x144137c5c is the only write of helper+0x108 in the exe, so a pointer swapped at Start stays for the device's life.
- Slots the device calls through helper+0x108 (byte scan of every `mov r,[r+0x108]` after a `[r+0x30]` load in .xtls and .data1, plus a register/stack dataflow pass over every .pdata function in 0x144137000..0x144156000): +0x00 FileWrite(name, data, size) -> bool (`Game_Save_UnmountSave` 0x14414a173), +0x08 FileRead(name, buf, size) -> int32 compared with size (mount 0x1441465ec, 0x14414283a, 0x14414518f), +0x30 FileDelete(name) (wipe 0x14413a971), +0x68 FileExists(name) -> bool and +0x78 GetFileSize(name) -> int32 (0x14414512d, 0x144145153), +0x80 GetFileTimestamp(name) -> int64 seconds, times 10,000,000 (0x1441427c2), +0x90 GetFileCount() -> int32, +0x98 GetFileNameAndSize(i, int32 *or 0) -> const char *, +0x1c8 BeginFileWriteBatch() / +0x1d0 EndFileWriteBatch() (0x144152070, only when +0x3e8 and the helper are set). No other slot is reached through the helper.
- Other remote storage users: the context's version string has one reference, and the context has three users: InitDevice, `Game_Read_GameConfig` (IsCloudEnabledForApp +0xb0, only to log "Cloud Storage has been disabled") and `Ne_CloudUploader_Upload` 0x1447c5bc0, which fetches the global interface itself and does FileWriteStreamOpen/WriteChunk/Close (+0x48/+0x50/+0x58), FileShare (+0x38) and two calls on interface 0x145f985d0. Its only caller is device slot +0x58, `Ne_SaveSystem2Win_WriteInfoXml` 0x144141c00, which is the corrupt-save upload: it downloads every remote file of a save through the helper into a temp dir, writes info.xml (`save_information`), zips it as `%s%I64u.zip` with the SteamID64 and uploads it. A sandbox that only swaps helper+0x108 would let this zip the sandbox's saves and upload them to the player's cloud, so the sandbox must also neutralise slot +0x58 (a per-object copy of the 16-slot vtable with +0x58 returning an error, or a wrap of 0x144141c00).
- Files on disk in cloud mode: every load and save mounts into a fresh temp dir from `Ne_SaveSystem_CreateTempDirectory` 0x144143580 (GetTempPathW + GetTempFileNameW, so `%TEMP%` in the Proton prefix), copies remote files in with FileRead + CreateFileW/WriteFile, and the unmount reads them back (FindFirstFileW/CreateFileW/ReadFile), FileWrites them and deletes the mount dir. helper+0x00 is never a path the device opens: mount (0x144145bfd), the wipe, the unmount and the enumerator use it only to strip the user-data prefix from the title dir before turning it into the remote prefix `savegame@` (backslashes to @, last one to #). So rewriting helper+0x00 alone redirects nothing and, if it stops being a prefix of the title dir, breaks the remote names the device matches; leave it alone. With the proxy in place the only disk writes are the transient temp mount dirs (prefix %TEMP%) and whatever the proxy writes.
- Local mode: `Game_Read_GameConfig` writes save system+0x498 from the engine setting `Steam.cloudEnabled` (default true) right before it calls InitDevice (0x1407fa7c0); IsCloudEnabledForApp is only logged. With it false (L1 here: from the log strings "using FindFirstFile instead!" and "unmounting save, m_storeInCloud is false", plus the wipe's +0x3e8 test) the device walks and copies `g_Ne_TitleSaveDir` (FindFirstFileW, CopyFileW, and the wipe deletes and recreates that folder) and skips FileWrite and the write batch. That folder is `<GetUserDataFolder>\savegame`, i.e. the player's real `userdata/<id>/3059520/local/savegame`, built before InitDevice from a separate GetUserDataFolder call unless the wide buffer at [0x146ca5e50]+0x180c is already filled. So local mode is not a sandbox by itself: it also needs the title dir redirected before the config read, and the helper still exists. The proxy is simpler and stronger.
- Fail-closed checks at Start (all L2 here): `*(void **)device == vt_Ne_SaveSystem2Win` and its slot +0x08 is `Ne_SaveSystem2Win_Start`; device+0x30 non-null (null means a non-Steam or local build, nothing to proxy); helper+0x108 non-null with a vtable outside the game image; device+0x3e8 logged. Second line: every save load and save goes through `Ne_SaveSystem_BuildSaveInfoList` 0x14413b6f0 (Enumerate, SelectAndLoad, SelectAndSave, SelectAndDelete) and `Ne_SaveSystem2Win_Mount` 0x144145650 (SelectAndLoad 0x14413f1c4, SaveSelected 0x144152290) before any remote read; both have func_start signatures. The wipe (+0x78) and the corrupt upload (+0x58) do not mount.
- Needs an independent verify: Ne_SaveSystem_InitDevice, Ne_SaveSystem2Win_Start (corrected slot list), vt_Ne_SaveSystem2Win, k_Ne_SteamRemoteStorageContext, k_Ne_SteamUserContext, g_Ne_TitleSaveDir, Ne_SaveSystem2Win_Mount, Ne_SaveSystem_BuildSaveInfoList, Ne_SaveSystem2Win_WriteInfoXml (corrupt upload), Ne_CloudUploader_Upload.
