# gamedb: GVDB game value database (code side)

Owner: see `subsystems.tsv`. Data-side format: research/gamedb.md. Cap analysis: research/grid24-cap.md §1.

## Map
- `Gdb_Load_GameDatabase` (0x1445a0350) references `game_package/gamedatabases/`, `gamedatabases.bin`, `GameDatabase.fileName`.
- Keys are `fnv1a64(dotted path)`. 1,108 code sites load key hashes as 64-bit immediates (`db_keys.tsv`, L1, from `work/exe/db_key_immediates.txt`); 92 have known paths.
- **Row counts** {#instancecount}: `Gdb_Init_TableCursor` (0x1445a25c0) builds `<container>._<row>_instancecount_` at runtime, looks it up with `Gdb_Lookup_Key`, caches it at `GdbTableCursor.row_count` (+0x200, < 0 = not cached). Missing key = 0 rows. Every tool that adds DB rows must bump the matching `_instancecount_` key.
- Field reads by name: `Gdb_Get_FieldInt(row, "max_entrants", 0)`; rows by label: `Gdb_Find_RowByLabel` (independent of row counts).

## Value map {#value-map}
The database object (`GdbDatabase`, held in `g_Gdb_Database`) is built by `Gdb_Load_GameDatabase` (0x1445a0350), which is its constructor and loader in one. The values live in `GdbDatabase.map` (+0xa8), a martinus robin_hood flat map of `GdbValueSlot {u64 key; record *value}` with max load 80% (`GdbValueMap`). Slots and info bytes are one block from the GVDB record allocator (`GdbDatabase+8`, vtable 0x145bee810, slots `Gdb_RecordAlloc_AllocBlock`/`Gdb_RecordAlloc_Free` forward to the GAME_VALUE_DB heap at +0x90); records come from the same allocator (`g_Gdb_RecordAllocator` vt+0x18). The eleven `Gdb_Unk_1445a6xxx` vtable slots are this allocator's.

**Load path.** In order, in `Gdb_Load_GameDatabase`: write the vtable and the record allocator; initialise the empty map (0x1445a04dd..0x1445a0535: mult 0xc4ceb9fe1a85ec53, keyvals = info = &mask, count = mask = max = 0, info_inc 0x20); set `g_Gdb_Database` (0x1445a053e); load `gamedatabases.bin` into a buffer (u32 record count, then records `{u64 key, u8 tag, u32 len, text[len], nul}`); **reserve** for max(file count, map count) (0x1445a09fc..0x1445a0aa3: smallest power of two N >= 8 with N*80/100 >= target, then `Gdb_HashMap_Rehash(&db->map, N)` if N > mask+1); insert every record with `Gdb_HashMap_Insert` (0x1445a0c3b, 0x1445a0e17; the loop bound is the file count saved at `[rsp+0x88]`); set `GdbDatabase.loaded` (0x1445a0f41). The game never inserts after that: `Gdb_HashMap_Insert` has no other caller, and `Gdb_HashMap_Rehash` has only the reserve and the insert's growth (`site_Gdb_InsertGrowCall`). The 629 readers of `g_Gdb_Database` (590 `.xtls`, 39 `.data1`, scanned by register tracking) are inlined lookups that read mult, keyvals, info, mask, info_inc and shift on every call; none reads count, max or the map base, and nothing else is sized from the map.

**Why 838,860.** The stock file has 742,857 records, so the reserve picks 2^20 buckets and `max_num_elements_allowed` = 1,048,576*80/100 = 838,860. An insert of a new key when count = max (or after an info-byte overflow with info_inc < 3) runs `Gdb_HashMap_Rehash` to 2^21. That function copies each slot pair into the new block and then destroys the old slot's record (record vt+8, 0x1445a6c09) and frees it (0x1445a6c1b): a game bug that never fires in stock, because the reserve always covers the file. After it every slot points at freed memory, and the first reader faults: `Gdb_Init_TableCursor`+0x31c (0x1445a28dc `mov ecx,[rax+8]`, the `_instancecount_` value) under `Loc_LocaleModule_Init`, the crash before 1.5.11. Info overflow below the growth point halves info_inc in place (no rehash); that path is safe.

**Sizing.** The map can be sized only between its initialisation and the first insert. `site_Gdb_ReserveTarget` (0x1445a0a11, sig `gamedb.reserve_target`, kind mid) is that point: rcx = the reserve target and feeds nothing else; raising it to T makes the game reserve for T records. Calling `Gdb_HashMap_Rehash(&db->map, N)` there (empty map, N a power of two >= 8) is equivalent. `Gdb_Load_GameDatabase` entry is too early (the init overwrites the map). N records need the smallest power of two N_b >= 8 with N_b*80/100 >= N: 2^20 holds 838,860 (17.0 MiB block), 2^21 1,677,721 (34.0 MiB), 2^22 3,355,443 (68.0 MiB). The core's design for round 3 is in `work/std16/W7-SIZING.md` of the std16/w7 worktree: a mid hook at the reserve site raising rcx to file count + older addons' edits + registry keys + 32 probes + 4,096, capped at 2^21 until T129 proves 2^22, and `swofty/registry/room.json` written after the boot apply. Tests: T127 (the site's registers), T128 (a 2^21 boot past 838,860), T129 (the 2^22 heap ceiling).

## Label-keyed side data {#side-data}
Readers find a row's data through names as well as through the row's own keys. `Gdb_Find_RowByLabel(<container>, <rows word>, <name>)` (independent of row counts) takes a name built from the row: its label, the label plus a suffix, a folder of a path field, or a field value. Other rows hold the row's label or `stat_id` by value. Game files are named after the same names. An `add-row` copy gets the source's keys and none of this; under a new label every such lookup misses. A missed row lookup is silent: the reader skips the block and keeps its defaults. A found row that lacks a key the reader asks for reads the missing-key sentinel (`Gdb_Get_FieldInt` mode 0, index -1).

The launcher's build check (`packages/core/src/dbedit/deps.rs`, docs/reference/ops/database.md#the-side-data-check) encodes the confirmed lookups above (presets, branding and TrackDataSet by `game_setup_modes`, pit times by `team`) as `RULES`, which warn. Name and value matches with no known reader are counted in one line per addon and listed by `swofty build --side-data`; matches in tables of other game areas (`AREAS`: career, story mode, F1 World, online, front end, customisation, unnamed) are listed only. Game files are outside it. A new confirmed reader goes into `RULES` with its address.

### Hunting a lookup {#side-data-hunt}
1. **Name scan.** `swofty db deps "<row selector>"` lists the names derivable from a stock row, the rows of other tables labelled with each, the fields that pick the row by label or `stat_id`, and how many unnamed keys hold the label (unnamed keys that reference the row).
2. **Deep keys.** The catalogue only names keys some name list reaches. `tools/gamedb/deepkeys.py <row> --depth 1..3 --level N=<vocabularies>` hashes `<row>.<w1>.<w2>.<w3>` with the prefix hashed once and FNV-1a continued per word; when the last level is small it unwinds the whole key set by each word (FNV-1a is invertible) and searches the earlier levels against the result. The setup presets came out of `--level 1=containers --level 2=exe --level 3=table:car_setup.sliders.slider` in 2.5 minutes. Found keys go into `tools/gamedb/compositions.txt`, then `row_keys.txt.gz` and the catalogue are regenerated.
3. **Reader.** Search the exe for the rows word or a slider name, decompile with `re/tools/decomp <addr>` (Ghidra project in /mnt/work/VSC/f1-modding). Table names are often stack-built: in 0x140c04fd0 `car_setup.presets` is two 8-byte immediates (0x757465735f726163, 0x7465736572702e70) plus `s`, so string search finds only `vehicle_package_setups`.
4. **Runtime A/B.** Run the same session with the stock-named row and with the copy. Game-log channels: `SWOFTY_GAME_LOG=info`, `SWOFTY_GAME_LOG_CHANNELS="default,VEHICLE_COLLISION_WORLD*:info,VEHICLE_ASSETS:info"`, and `SWOFTY_GAME_LOG_REPEAT` set high: the repeat cap counts per format string, so lines of later sessions are suppressed at the default. Plank contacts show on `VEHICLE_COLLISION_WORLD*`, missing package resources on `VEHICLE_ASSETS`.

## Open
- The eleven `Gdb_Unk_1445a6xxx` functions are slots of the record allocator vtable 0x145bee810 (see Value map); only +0x10 and +0x38 are named. Slot +0x18 (0x1445a6330) allocates records.
- The GAME_VALUE_DB heap's budget, if it has one (T129).
- EA: the reserve site needs an overlay pattern from a decrypted dump; without it the core reports the pre-size as unavailable.
- `Gdb_Unk_14305c1f0` was labelled onGameValueDbLoaded but its strings are network logging.
