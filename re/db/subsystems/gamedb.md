# gamedb: GVDB game value database (code side)

Owner: see `subsystems.tsv`. Data-side format: research/gamedb.md. Cap analysis: research/grid24-cap.md §1.

## Map
- `Gdb_Load_GameDatabase` (0x1445a0350) references `game_package/gamedatabases/`, `gamedatabases.bin`, `GameDatabase.fileName`.
- Keys are `fnv1a64(dotted path)`. 1,108 code sites load key hashes as 64-bit immediates (`db_keys.tsv`, L1, from `work/exe/db_key_immediates.txt`); 92 have known paths.
- **Row counts** {#instancecount}: `Gdb_Init_TableCursor` (0x1445a25c0) builds `<container>._<row>_instancecount_` at runtime, looks it up with `Gdb_Lookup_Key`, caches it at `GdbTableCursor.row_count` (+0x200, < 0 = not cached). Missing key = 0 rows. Every tool that adds DB rows must bump the matching `_instancecount_` key.
- Field reads by name: `Gdb_Get_FieldInt(row, "max_entrants", 0)`; rows by label: `Gdb_Find_RowByLabel` (independent of row counts).

## Label-keyed side data {#side-data}
Readers find a row's data through names as well as through the row's own keys. `Gdb_Find_RowByLabel(<container>, <rows word>, <name>)` (independent of row counts) takes a name built from the row: its label, the label plus a suffix, a folder of a path field, or a field value. Other rows hold the row's label or `stat_id` by value. Game files are named after the same names. An `add-row` copy gets the source's keys and none of this; under a new label every such lookup misses. A missed row lookup is silent: the reader skips the block and keeps its defaults. A found row that lacks a key the reader asks for reads the missing-key sentinel (`Gdb_Get_FieldInt` mode 0, index -1).

### Hunting a lookup {#side-data-hunt}
1. **Name scan.** `swofty db deps "<row selector>"` lists the names derivable from a stock row, the rows of other tables labelled with each, the fields that pick the row by label or `stat_id`, and how many unnamed keys hold the label (unnamed keys that reference the row).
2. **Deep keys.** The catalogue only names keys some name list reaches. `tools/gamedb/deepkeys.py <row> --depth 1..3 --level N=<vocabularies>` hashes `<row>.<w1>.<w2>.<w3>` with the prefix hashed once and FNV-1a continued per word; when the last level is small it unwinds the whole key set by each word (FNV-1a is invertible) and searches the earlier levels against the result. The setup presets came out of `--level 1=containers --level 2=exe --level 3=table:car_setup.sliders.slider` in 2.5 minutes. Found keys go into `tools/gamedb/compositions.txt`, then `row_keys.txt.gz` and the catalogue are regenerated.
3. **Reader.** Search the exe for the rows word or a slider name, decompile with `re/tools/decomp <addr>` (Ghidra project in /mnt/work/VSC/f1-modding). Table names are often stack-built: in 0x140c04fd0 `car_setup.presets` is two 8-byte immediates (0x757465735f726163, 0x7465736572702e70) plus `s`, so string search finds only `vehicle_package_setups`.
4. **Runtime A/B.** Run the same session with the stock-named row and with the copy. Game-log channels: `SWOFTY_GAME_LOG=info`, `SWOFTY_GAME_LOG_CHANNELS="default,VEHICLE_COLLISION_WORLD*:info,VEHICLE_ASSETS:info"`, and `SWOFTY_GAME_LOG_REPEAT` set high: the repeat cap counts per format string, so lines of later sessions are suppressed at the default. Plank contacts show on `VEHICLE_COLLISION_WORLD*`, missing package resources on `VEHICLE_ASSETS`.
