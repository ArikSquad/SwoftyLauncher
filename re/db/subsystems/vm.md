# vm: UI view-model registry

Owner: see `subsystems.tsv`. Write-up: research/exe.md §1 (conventions), §3.4; research/ui-native.md (binding, dispatch, screens, routes). The format side (what a `.ui` node must contain) is in [`ui_system.md`](ui_system.md); the user-facing page is `docs/reference/ui/engine.md`; the machine-readable checks are `re/db/ui/loader_rules.json`.

Markers used below: **[L2]** decompiled and read with callers listed (the row is L2); **[L2, run]** the same, and also observed in a live gdb trace with `re/tools/ui_trace` on 2026-10-23 (logs not filed as a T### run, so no row is L3); **[L1]** pattern, scan or rules-file only; **[inferred]** a reading no decompile or trace confirms.

## Map
- `g_Vm_Registry` (0x146ca54f8) is the registry singleton pointer; T000 saw it non-null after the main window appeared.
- `Vm_Set_String(reg, parent, name, NeStr**, overwrite)` → `Vm_NodeSet_String(node, v, 0, 1)`; `Vm_Set_Bool(...)` → `Vm_NodeSet_Bool`. `Vm_Set_Int` (0x140d38fd0) and `Vm_Set_UInt` (0x140d38210) are the int/index siblings. overwrite=1 replaces an existing value.
- `parent` for an item's properties is `HomeItem.button_node.node + 8`; with no node use `k_Vm_EmptyNodeHandle` (0x146ca0e90).
- Node names and commands are djb2 hashes (`h_*` anchors); components use md5-64 (ui.md).

## UI node-class (widget) registry {#classes}
Every `.ui` node has a 4-char class FourCC. 136 classes are registered in all: the 97 neon classes below and the game's own (`F1xx`, `TILE`, `LCDC`, `OSPL`, `RSCM`, `TACM`, `TADM`, `UISS`) registered in 0x1437ea4a0 **[L1]**. Each class has one vtable whose slot 16 (+0x80) returns its FourCC, slot 9 (+0x48) is its from-data init, slot 43 (+0x158) its message handler and slot 50 (+0x190) its pin handler **[L1]**; `loader_rules.json` `classes` lists all 136 with addresses, and the vtables recorded so far are `vt_Vm_UiGroup`, `vt_Vm_Tile`, `vt_Vm_F1TileSpawner`, `vt_Vm_AudioThemeTrigger`, `vt_Vm_UiLabel`, `vt_Vm_UiScreen`, `vt_Vm_UiScrollBar`, `vt_Vm_UiTabController`, `vt_Vm_SingleValueDecision` (all L1: no decomp of the factory create that installs them yet). `Vm_Register_NodeClasses` (0x14419b1d0, L2) constructs ~97 class-factory objects (each 0xc0 bytes: vtable at +0x00, FourCC tag at +0x10) and installs them through the callback `Vm_Install_NodeFactories` (0x1441cac40, L2), which does `Vm_Find_NodeFactory(mgr, fourcc)` (0x14416bc70) per class and registers the factory at `mgr+0x8210`'s vtable+0x38. `Vm_Build_UidfNode`, the screen job and `Vm_Build_TemplateNode` look a node's class up with `Vm_Find_NodeFactory` (L2: a hash map keyed by the u32 FourCC, null on a miss); a FourCC with no factory, or a factory that returns null, fails the node with code 5 (0x1441ddc1c screens, 0x144181765 templates) **[L2]**.

## Load: templates and screens {#load}
`Vm_Load_UidfResource` (0x14449e140, L2) is the UIDF resource handler, run once per `.ui` resource. It walks the fragments in order **[L2]**:
- `temp` (Screens, Flows) → `Vm_Load_UidfScreens` (0x1441d7a90, L2) queues a 0xd0-byte build job on mgr+0xb900; the UI update (0x1441db170) builds the screens over later frames (sites `site_Vm_UidfJob_*`).
- `syst` (Templates) → `Vm_Load_UidfTemplates` (0x144177470, L2, call 0x14449e28c), synchronous.

## Template store and instantiation {#templates}
**Registration [L2].** `Vm_Load_UidfTemplates` parses no node data. Per template it reads only `name` and stores a `UiTemplateRecord` (`structs/UiTemplateRecord.h`: `NeStr* name` +0, resid* +8, pkg base +0x10, u32 node reference +0x18, ctx +0x20) in the template store at `*(uisys->vt[0x48]() + 0x8168)` (= `*(mgr+0x8168)`; name map +0x28 keyed by the name string, record array +0x50/+0x58). The store is **global across every loaded `.ui`**. A name already in it makes the loader return 0x58 (0x144177f61; trace site 0x144177cfd); `Vm_Load_UidfResource` then destroys the resource's tracker and stops (0x14449e292), so every later template of that resource is never registered. The record's node reference is a `!pkg` CHUNK reference (`0x80000060`, `0x800001f0` in the live trace) **[L2, run]**.

**Instantiation [L2, run].** Every runtime instantiation looks the record up by name and calls `Vm_Instantiate_Template_Thunk` (0x144177fe0, `jmp` to the `.data1` body `Vm_Instantiate_Template_Body` 0x153215c10) with `&rec->node_ref`, `rec->pkg`, the parent and the instance name. A name that is not in the store is skipped by every caller without a log. Callers (9): the tab controller (0x144267084 in `Vm_UiTabs_AddTabTemplate`), `Vm_Spawn_TemplatesFromList` (0x144178607), the `F1TS` tile spawner (0x1438310f1 in 0x1438308c0), and 0x143816380, 0x1442541e4, 0x14425e2ff, 0x14427f793, 0x14429a6c8, 0x14429e99a. The template tree is built again on every instantiation.

The body:
1. calls `Vm_Build_TemplateNode` (0x1441815c0, call 0x153215d00) under the parent;
2. on rc != 0 jumps to its exit (0x153215e71) with no detach and no destroy;
3. on rc 0 runs the stack visitor `vt_Vm_InstanceRemapVisitor` (0x145a74ad0), whose slot 2 `Vm_Remap_InstanceSignals` (0x144349300, call 0x153215d64) rewrites each signal `to_object` that names a node inside the template to its runtime id (ids outside the template stay as authored, no error);
4. calls root vt+0x58, then root vt+0x50(ctx), whose rc becomes the instance result (0x153215dbd; trace site 0x153215dbf), then sends a 0x603 message to the nearest `UISE` ancestor. Out = `{node*, rc}`.

**`Vm_Build_TemplateNode` [L2, run]** (recursive; sibling of `Vm_Build_UidfNode` for screens): `Vm_Read_UidfNode` (rc site 0x14418160a; node record: name `char*` +0x68, FourCC +0x70, object +0x78, children +0x10) → `Vm_Find_NodeFactory(rec+0x70)` (null → 5 at 0x144181765) → factory create → obj vt+0x38 → obj vt+0x48 init(rec) (rc site 0x144181657) → only on init rc 0: attach to the parent with parent vt+0x170 (0x14418169e) → runtime id = djb2 continued from the parent id with `"." + name` (the root uses the instance name, and node+0x14 = djb2(instance name)) → push (authored id, runtime id) into the remap table → build the children in order; the first non-zero child rc stops the loop and is returned. Every exit passes 0x14418176a with rdi = record, eax = rc. No log on any path.

**Data-driven spawner [L2].** `Vm_Spawn_TemplatesFromList` (0x144178270, caller 0x1442a4839) instantiates one template per entry of a VM list, reading `template_path` (djb2 0xbe8c38ed), `data_context_root_path` (0xbc9e9732), `signal` (0x1bc6ade3) and `signal_data` (0x0c6d6d7c); an unknown template or a failed instance skips that entry.

## Tabs (`UITC`) {#tabs}
- **Tab VMs [L2, run].** For `f1_world_activity_container`, `Game_F1WorldActivityContainer_AddTabs` (0x141a76130, game lane) builds seven tab view models (vector at vm+0x2c8) with the template names, in order: `f1_world_activity`, `f1_world_activity_offline`, `dynamic_era_select` (lng_solo_grand_prix), `public_gp_select`, `dynamic_era_select` (lng_time_trial), `dynamic_era_select` (lng_screen_era_select), `session_create_dlc_select_tab` (registered by `f1_world_container.ui`). The template `time_trial_select`, which `f1_world_activity_container.ui` also registers, is not used by any tab. The live trace built exactly these seven content templates in this order.
- **Controller [L2, run].** `Vm_UiTabs_OnMessage` (0x144264d50, `vt_Vm_UiTabController` slot 43 at 0x145a6b068) handles the data-context message: it resolves the `tabs` and `tab_headers` VM arrays and calls `Vm_UiTabs_AddTabTemplate` for every tab with `content_template` (call 0x144265241; the result is discarded), then in a second loop with `header_template` (call 0x1442657c0; the header instance is recorded). A NULL result does not stop either loop. Live: content loop for all seven tabs, then header #1..#7, each building `primary_nav_tab` from `templates/tab_header_templates.ui`. Destroy site 0x144265036.
- **One tab [L2, run].** `Vm_UiTabs_AddTabTemplate` (0x144266e30) resolves the tab entry key it was given (for the store lookup) and always `content_template` (for the name). The instance name is `tab_<n>( <content_template> )` (`"%hs%I64u( %hs )"`), with `<n>` = the controller's child count (+0x18 vector) + 1; with a header index the full name gets a `.tab_<index>( … )` form. So **a header instance carries the content template's name**. Lookup miss (0x144267110) → NULL; record site 0x144266fa1; instance rc != 0 (0x14426708d) → NULL. On success: a `UITH` root (0x48544955) gets root[9] = controller, then the attach point (vt+0x108) and visibility (vt+0xd0) are set. Neither failure logs.
- **Live, breaking era build [run].** `tab_3( dynamic_era_select )` failed with rc 3 (root init, see [behaviours](#behaviours)) and the next content instance was named `tab_3( public_gp_select )`: the child count did not grow, so the failed root was never attached. All three era content instances failed this way; the seven header instances all built.
- **[inferred]** The controller then holds four content instances for seven tabs while its headers are complete. How it maps a selected tab to its content instance is not mapped; a shifted mapping would explain the vanished play screen and a result that depends on which tab is selected first.

## Element init and behaviours {#element-init}
`Vm_ElementBase_Init` (0x1441ffb90, L2) is the init of 20 classes and is called from the init of 106 more (126 of 136, **[L1]** scan). In order **[L2]**:
1. class FourCC (vt+0x80) == record `type`, else 5;
2. slot 4 (layout): only `path = slot4[0]` is read; an empty path → 0x22; each step needs `componentId` when it has `isComponentId` (step kind 1), else `nodeId` (kind 0), else 3. The steps go to the attach behaviour ([layout attach](#layout-attach));
3. slot 5 (components): the first entry needs `name` and `componentId`, else 3; it adds one more step;
4. slot 6 (behaviours): each entry needs `type`, else 3; a type the behaviour registry (uisys+0x10, lookup 0x144161470) does not know is skipped; each created behaviour runs its from-data init (vtable slot 5, +0x28) in the loop at 0x14420254d (result site 0x144202550; 0x1442028c8 and 0x144202978 are the other behaviour-init sites the trace arms) and a non-zero rc is the element's rc.

Shared chain and concrete inits (ui-native.md §11): `Vm_ListBase_Init` (0x144208c80; UITG/UITB/UILT/UIL2/UIEL; its result is `Vm_Read_PropBinding(props,"data")`: no `dbentry` key → 3, missing/not an object/empty → 5), `Vm_UiToggle_Init` (0x144272810, UITG), `Vm_UiSlider_Init` (0x1442593b0, UISL; flags with `Vm_Read_PropBool` at +0xa4..+0xa7/+0x18, then PropBinding data/value/min/max/step, all int), `Vm_SingleValueDecision_Init_Thunk` (0x144276f20, SVCD, L2: element base, then `dbEntry` 0xfe80e13d and 0xd07f8d2e optional, `value` 0x425ed3ca whose read rc is returned). The `F1TS` init 0x14382cff0 rejects an `inputType` other than `normal`/`dpadOnly` with 0x57 (**[L1]**, rules file; no KB row). Property readers: `Vm_Read_PropBinding` (0x14417e200), `Vm_Read_PropBool` (0x144206120), `Vm_Read_PropObject_Thunk` (0x14417f1b0 → `.data1` 0x153258c90; missing key → 3, unreadable → 5), all finding keys through `Vm_Find_PkgObjectKey_Thunk` (0x143927f90 → `.data1` 0x151d329f0): a **case-insensitive string compare of the key names, not a hash lookup**; a miss returns 3 **[L2]**.

## Layout attach {#layout-attach}
`Vm_GetOrCreate_AttachBehaviour` (0x144179710, L2) returns the node's attach behaviour (`vt_Vm_AttachBehaviour` 0x145a73fa0, L2, 0x50 bytes, secondary vtable 0x145a74030), creating it on first use. Its +0x20/+0x28/+0x30 vector receives one `UiLayoutStep` (`structs/UiLayoutStep.h`, 0x30 bytes: u8 kind +0 (0 nodeId, 1 componentId), u32 nodeId +4, u64 componentId +8) per path step **[L2]**. No step is resolved against the `.idf` at load, so no load-time check depends on the scene. Resolution happens when the element attaches to the scene (`attacherOpened`/`attacherClosed` pins, `UI_ATTACHER` channel transitions in 0x144218810); how a step descends through `eXRef` and `eMask` elements is **not mapped**.

## Signals, commands and events {#signals}
- **Reading [L2].** `Vm_Read_CommandList` (0x1442c29e0, NeUICommandList secondary vtable slot 0x145a70718) and `Vm_Read_EventList` (0x1442c2fd0, NeUIEventList slot 0x145a707b8) build one 0x30 object (vtable 0x145a744f0) per slot-2 / slot-3 entry and fill it with `Vm_Read_SignalList` (0x1442c17e0): the key `command` (fnv1a32 0x93594ab2) / `event` (0xfe30d09f) is required, and `signals` (0xc3c68e0e) is required (an empty array is fine); else 3. Each signal is a 0x18-byte `UiSignal` (`structs/UiSignal.h`): `to_pin` (0x40d4ab10) at +8 and `to_object` (0x0c3e545e) at +0xc are required, else 3; `attributes` (0xe1ffdb94) are optional; each `mappings` (0xcedfea42) entry needs `value`, else 3. `commandName`, `eventName`, `to_object_name`, `to_pin_name` and `from_pin_name` are never read. Any non-zero rc fails the node.
- **Linking [L2].** `Vm_Link_NodeReference` (0x144179da0, callers 0x14427f2c8, 0x144280545) resolves a node id; a hit links it and logs `UIRef` `LINK node1 [%s][%u]` (channel 0x0a325568, info level); a miss registers a **pending link** (0x1442238b0) that completes when a node with that id is created. No error either way.
- **Raising [L2].** `Vm_Raise_NodeEvent` (0x1442468d0, 226 call sites, queue = uisys+0x230) finds the event id in the node's event list; an undeclared event or one with zero signals returns 0 (a no-op); otherwise it queues (ring of 1000 x 0x20 at queue+0x50) or dispatches now.
- **Delivery [L2].** `Vm_Dispatch_EventSignals` (0x144251800) takes target = `**signal->link`; a null handle or target skips the signal silently; otherwise target vt+0x190 (pin handler) then vt+0x198. There is no error path: a pin the target class does not implement is ignored by that class's handler.

## Failure modes and blast radius {#failures}
| failure | what it takes down | log | evidence |
|---|---|---|---|
| node in a **screen** build job (rc not 0/0x57) | the screen and every later screen of the same `.ui` (`site_Vm_UidfJob_ScreenDone` 0x1441de0d7); 0x55 (same-name screen, `Vm_Read_UidfNode`) skips only that screen | none from the game; swofty_core logs `[ui] engine screen '…' failed to build` | L2 |
| a descendant node in a **template instance** | the whole instance; the rc reaches every ancestor; the root and every node built before the failure stay attached to the parent without vt+0x58, signal remap or vt+0x50 | none | L2 |
| the **root** init of a template instance | the instance; nothing is attached, the root object leaks | none | L2, run |
| a failed **tab content** instance | dropped by `Vm_UiTabs_AddTabTemplate` (NULL, discarded by the content loop); the controller's child count does not grow, so later instance numbers shift | none | L2, run |
| template name not in the store at instantiation | that one instance (every caller skips it) | none | L2 |
| duplicate template name at load | every later template of that resource; which resource wins depends on load order | none | L2 |
| signal target not created yet | the signal stays pending; anything fired before the target exists is dropped | none | L2 |
| event without signals, undeclared event, unhandled pin | nothing happens | none | L2 |

Other order-dependent paths: tab templates are instantiated on the controller's data-context message, which can come before or after `FeTile_Build_EraTiles` (0x141a6e980; core's `site_FeTile_EraTilesBuilt` 0x141a6f728 creates `addon_tiles`/`addon_tiles_visible` there; in the fixed-build session the era tile build first ran after all fourteen tab instances; in the breaking-build session it never ran) **[L2, run]**; bindings such as `F1TS dataContext` and `SVCD dbEntry` store a path at init and resolve it later (binding watcher 0x144209390) **[L1]**.

No code on the screen-build or template path logs a failure. The engine's errno trace (`Ne_Set_ErrnoTrace` 0x14391ab70, gate `g_Ne_ErrnoTraceOn` 0x1461078d0, ring `g_Ne_ErrnoTraceRing` 0x146107830, core lane, L2) records `{return address, code}` from failing readers for one armed thread; nothing in the shipped game arms it for the UI thread.

## Node helpers {#nodes}
- `Vm_Resolve_RegistryNode` (0x1442b1b60, L1, **2166 refs**): resolve a `g_Vm_Registry` node by a path-string token (`#ui_menu_data.…`, `view_model_data.…`, `network.…`). The core VM lookup — frontend and HUD VMs both go through it. `Vm_Link_RegistryNode` (0x144179360, 918 refs) links the resolved node into a holder/handle.
- `Vm_GetOrCreate_ChildNode` (0x1442b2bf0, L2): resolve/create a child node under a parent; `k_Vm_EmptyNodeHandle` on miss.
- `Vm_Resolve_NodePath_Thunk` (0x1442b2770) is the path-resolve used by `Vm_Apply_BindingEvent` and the core `set_*` API.
- `Vm_GetOrCreate_ListChild` (0x1442b30e0, L2, sig `vm.get_or_create_list_child`) is the list-node twin of `Vm_GetOrCreate_ChildNode`: it keeps an existing child only when the child's vt+0x10 is true (list node) and otherwise creates one with 0x1442b2f70; `Vm_GetOrCreate_ChildNode` keeps vt+0x28 children (object nodes) and creates with 0x1442b2a50. `Vm_Set_NodeRef` (0x14083c270, L2, sig `vm.set_node_ref`, bound through its call 0x141a6eeb9 in `FeTile_Build_EraTiles` because the setter template clones share its prologue) links a new child by list append (0x1442b32b0) or keyed insert (0x1442b3770) on the same split. The era picker's addon row uses both. A node created earlier under the same name with the other kind is not the node core fills **[inferred]**.

## Routing {#routes}
- `Vm_Fire_Route(router, vm, &name, flag)` (0x1442c0e20, L2, 266 callers): looks the VM's node up in the router robin-hood map (router+0x48), finds the `UISE` route-group element and calls the route runner.
- **`Vm_Run_Route` (0x144188370, L2)** is that runner (previously unmapped, ui-native.md §9): `void(uiSys, node, routeName, group, int, a6, a7)`, invoked as `Vm_Run_Route((*uiSys)->vt[0x1c0](), node, name, group, 0, flag, 0)`. It runs the route steps and is where a missing-screen step raises its error — the single hook point for the route guard, covering both native `Vm_Fire_Route` routes and data-fired UIAC pins.
- Route-command executors (slot +0x58 of each route-cmd vtable): `Vm_RouteCmd_ResolveTargetScreen` (0x144187620), `Vm_RouteCmd_OpenScreen` (0x143889310) → `Vm_Open_Screen` (0x144182660).
- `Vm_Update_FlowStateMachine` (0x144423ce0, sig `vm.flow_update`) ticks the flow state machine each frame; it logs `State [%s] onUpdate returned LinkRoute [name,hash]` (0x144424e27) and drives screen navigation. The frontend-side states live in the `fe_flow` lane.

## Open

- How a layout step resolves through `eXRef`/`eMask` at attach time (0x144218810).
- The behaviour inits other than NBVN are read only in `loader_rules.json`; they have no KB rows.
